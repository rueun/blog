# 운영 중인 레거시 서비스를 AI와 함께 점진적으로 리팩토링 하기

## 시리즈 소개 문구

운영 중인 레거시 서비스를 멈추지 않고 바꾸는 과정은 늘 기술보다 순서와 판단의 문제에 가깝다. 이 시리즈는 실제 서비스 리팩토링을 진행하면서 왜 이런 결정을 했는지, 어떤 순서로 구조를 바꿨는지, 그리고 그 과정에서 AI를 어떻게 실무 파트너처럼 활용했는지를 기록한 글이다.

## 시리즈 한 줄 소개

운영 중인 레거시 서비스를 Spring Boot, Gradle, React Router v7 기준으로 점진적으로 옮겨가며 테스트, 구조, 도메인 분리를 어떻게 진행했는지 정리한 시리즈.

## 편별 썸네일용 한 줄 요약

### 1편. 운영 중인 서비스를 왜 지금 리팩토링하기로 했나
기능 추가가 점점 어려워진 운영 중 서비스에서 왜 전면 재작성 대신 점진적 리팩토링을 선택했는지 정리한 글.

### 2편. 왜 Spring Boot, Gradle, React Router v7로 방향을 정했나
팀이 계속 유지할 수 있는 구조를 만들기 위해 왜 이 기술 스택과 `/backend`, `/frontend` 구성을 선택했는지 설명한 글.

### 3편. 리팩토링 전에 Playwright 테스트부터 만든 이유
리팩토링 전에 현재 서비스 동작을 먼저 고정하기 위해 Playwright 회귀 테스트를 만든 과정을 정리한 글.

### 4편. AI가 잘 이해할 수 있는 구조를 먼저 만들었다
AI를 적극적으로 활용하기 위해 왜 프로젝트 구조를 먼저 정리하고 멀티모듈 기준을 세웠는지 다룬 글.

### 5편. Gradle 전환과 미사용 코드 정리부터 시작한 이유
좋은 구조를 만들기 전에 먼저 실행 기준과 dead code부터 정리해야 했던 이유를 설명한 글.

### 6편. domain과 infra를 나누며 백엔드 리팩토링을 시작했다
`posting` 도메인부터 domain과 infra를 분리하며 Spring Data MongoDB를 도입한 첫 단계를 정리한 글.
